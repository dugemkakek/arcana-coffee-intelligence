What v1 should actually do
For your own roastery MVP (then closed beta) the core should be three things:

Roasting telemetry & sessions (local app)

Inventory (green + roasted)

POS/e‑commerce sync → simple roast planning

AI sits on top as a paid layer that reads those three domains and talks back via JSON and narratives.

Core modules and features
1. Roasting telemetry & profiles
Think “Artisan + Cropster RI, but minimal”:

Live roast graph

Time vs BT, ET, RoR, with event markers (charge, TP, FC, drop).

Sample interval: 1–2 seconds.

Roast session model

Bound to: machine, green_lot, optional product (SKU), operator.

Store green_weight_kg, roasted_weight_kg, timestamps for charge/drop.

Profile library

Save any session as a RoastProfile reference.

Attach to product (e.g. “Ethiopia natural V60 profile”).

Replay (MVP = overlay only)

Show reference curve overlay while roasting; no auto-control yet.

You already did a lot of this in RoastMind; this is the same pattern, but generalized for SaaS.

2. Inventory: green and roasted
Inspired by Cropster’s green + roasted inventory and API.

Green inventory

GreenLot: origin, region, farm, variety, process, moisture, density, harvest year, supplier, contract qty, current stock.

Optional GreenMovement table for in/out/transfer, but you can add that later.

Roasted inventory

Product (SKU) with mapping to POS SKU.

ProductGreenMapping for blends (product ↔ many green lots with percentage).

RoastedInventory per product + location (on_hand_kg).

InventoryAdjustment records whenever stock changes (roast batch, sale sync, writeoff, manual adjust).

Minimal KPIs:

On-hand per SKU and per green lot.

Simple reorder alerts (if current_stock_kg < threshold).

3. POS/e‑commerce sync and planning
Take inspiration from Cropster API: sync green, roast inventory, and commerce orders.

Tables:

ExternalSystem (POS, e‑commerce; provider = Olsera, Shopify, WooCommerce, etc.).

ExternalProductMapping (external SKU ↔ internal Product).

ExternalOrder + ExternalOrderItem.

SalesAggregate per product per day (for AI and planning).

Flows:

Cron on local node:

Pull orders from POS API (or import CSV).

Map SKUs → products; write ExternalOrder/Item.

Produce SalesAggregate rows.

Planning job:

For each product: needed = min_stock + forecast - (on_hand + already_planned).

Suggest roast tasks: product, batch size, date, machine.

AI layer (paid tier)
1. Narrow but useful AI for MVP
Start with three abilities:

Roast profile analysis

Input: roast session data + (optionally) reference profile.

Output JSON:

scores for charge phase, Maillard, development.

flags for baked/underdeveloped/flick/crash.

summary_text (ID + English/Indonesian).

Production & inventory suggestions

Input: inventory snapshot + recent SalesAggregate.

Output: a proposed roast plan list (SKU, batches, dates) + explanation.

Roastery Q&A assistant

Input: natural language question + structured context (inventory, sales, roasts).

Output: text answer, plus optional machine-readable actions.

All exposed from an internal AI service as functions like:

POST /ai/roast-analysis

POST /ai/plan-production

POST /ai/qa

Each is just JSON in/out, which you can prompt and test easily in Claude Code.

2. Provider abstraction and billing
You want MiniMax as primary but swappable. So:

AiProviderConfig

tenant_id, provider (minimax, openrouter, local), model_name, encrypted api_key, max_tokens_per_call.

Adapters

MinimaxAdapter, OpenRouterAdapter, LocalLLMAdapter, all implementing same interface.

Fallback

Try primary, if timeout/5xx, fall back to secondary provider.

Usage tracking

AiUsageRecord with tenant_id, feature, tokens_prompt, tokens_completion, cost_estimate, created_at.

Plans:

Free plan: core features only.

Paid plans: AI endpoints enabled + usage caps.

Data ownership and local vs VPS split
You want local-first but with VPS aggregation and AI.

Pattern:

Local node (per roastery)

Hosts the main app (telemetry, UI).

Full DB: roast curves, events, local inventory, POS sync cache.

Central VPS

Multi-tenant DB: Tenant, User, plans, AI configs, usage.

Aggregates from each node: SalesAggregate, optional roast summaries.

AI services run here.

Ownership:

Raw roast data stays on local node by default.

Local node periodically pushes aggregates (and optional raw) to VPS over HTTPS with signed JWT.

Per-tenant sync policy:

“Aggregates only”

“Aggregates + raw curves”

“No sync” (pure offline, but then limited AI).

High-level architecture
Components
Very similar to Cropster RI client (local) + C‑sar online platform (central).

Local Roastery App

Stack: Node/TS or Python backend + React/Next front.

Responsibilities:

Phidget or other logger integration.

Local Postgres (or SQLite for dev) with all core tables.

UI for roast control, inventory, planning.

Sync worker to push aggregates + metadata to VPS.

Central SaaS Backend (VPS)

Multi-tenant API.

Global Postgres for tenants, AI usage, billing, cross-tenant analytics.

AI service with adapters.

Admin console UI for you + future roasteries.

Integrations

POS/e‑commerce connectors; for Olsera you can start by:

Polling orders API.

Or using cron to import CSV exports.

Green Coffee Supplier Marketplace Module
What it adds
A community layer on top of the core platform. Any verified roastery on the system can browse Indonesian supplier listings, submit purchase-verified reviews, and see AI-generated summaries of each supplier and lot.

Supplier directory
